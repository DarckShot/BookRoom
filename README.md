# BookRoom

Frontend-приложение для поиска и бронирования переговорных комнат. Пользователь может выбрать
офис, найти свободную переговорную на нужное время, посмотреть её расписание, создать
бронирование и управлять своими будущими встречами.

Проект выполнен в рамках
[тестового задания](./Frontend-trainee-assignment-autumn-2026.md). Директория `server` содержит
предоставленный вместе с заданием mock-backend и используется только как инфраструктура для
локальной разработки и проверки frontend.

## Возможности

- выбор офиса и фильтрация переговорных по дате, времени, длительности и вместимости;
- отображение доступности комнат для выбранного интервала;
- страница переговорной с информацией, расписанием и выбором свободного времени;
- создание бронирования с клиентской валидацией ограничений;
- отдельная обработка конфликта бронирования `409 BOOKING_CONFLICT`;
- просмотр предстоящих и прошедших бронирований пользователя;
- отмена собственного будущего бронирования;
- loading, error и empty-состояния основных экранов;
- обновление списка комнат и открытого расписания через WebSocket.

Реализованы дополнительные задания:

- автоматический reconnect WebSocket с REST-resync и индикатором потери соединения;
- real-time обновление всего списка переговорных;
- оптимистическая отмена бронирования с rollback;
- экспорт бронирования в `.ics`;
- создание еженедельной серии встреч.

## Требования

- Node.js 20 или новее;

- предоставленный mock-backend из директории `server`.

## Установка и запуск

Установить зависимости frontend:

```bash
cd frontend
npm ci
```

В отдельном терминале запустить предоставленный backend по инструкции из
[`server/README.md`](./server/README.md):

```bash
cd server
npm ci
npm run dev
```

Запустить frontend:

```bash
cd frontend
npm run dev
```

Приложение будет доступно по адресу `http://localhost:5173`, backend — по адресу
`http://localhost:3000`.

В development запросы к `/api/v1` и WebSocket-подключение проксируются Vite на предоставленный
backend. При необходимости другой базовый адрес API можно передать через `VITE_API_URL`.

## Маршруты

| Маршрут           | Назначение                           |
| ----------------- | ------------------------------------ |
| `/`               | перенаправление на `/rooms`          |
| `/rooms`          | список и фильтры переговорных        |
| `/rooms/:roomId`  | информация и расписание переговорной |
| `/bookings`       | бронирования текущего пользователя   |
| любой неизвестный | страница «Ничего не найдено»         |

## Архитектура frontend

```text
frontend/src/
├── api/          HTTP-функции, query keys/options и WebSocket-утилиты
├── assets/       SVG-иконки, сгруппированные по доменам
├── components/   переиспользуемые UI-, layout-, rooms- и bookings-компоненты
├── constants/    ограничения бронирования и статические опции
├── contexts/     контекст состояния WebSocket-соединения
├── hooks/        URL-состояние фильтров и UI/realtime-хуки
├── pages/        компоненты уровня маршрутов
├── router/       дерево маршрутов и централизованные пути
├── test/         тесты, fixtures и тестовые утилиты
├── types/        API- и доменные типы
└── utils/        чистая логика дат, времени, расписания и iCalendar
```

Backend считается источником истины. REST-данные принадлежат TanStack Query и не копируются в
отдельное глобальное хранилище. WebSocket-события инвалидируют соответствующие query keys, после
чего актуальное состояние повторно запрашивается через REST.

Состояние фильтров списка переговорных хранится в URL. Временное UI-состояние — открытая модалка,
значения формы и выбранное бронирование — остаётся локальным в компонентах и хуках.

Переиспользуемая логика часовых поясов и интервалов вынесена из компонентов. Локальные дата и
время офиса преобразуются в ISO 8601 перед отправкой в API.

## Принятые решения

- Выбранный офис и фильтры хранятся в URL, чтобы переживать обновление страницы, переходы по
  приложению и открытие общей ссылки.
- Сброс фильтров очищает все параметры, включая выбранный офис, и возвращает экран в исходное
  состояние.
- Все ограничения времени рассчитываются в `timezone` выбранного офиса. Часовой пояс браузера
  не используется как часовой пояс офиса.
- Frontend проверяет будущее время, рабочие часы `09:00–20:00`, минимальную длительность и шаг
  15 минут, а также горизонт 30 дней. Окончательное решение всегда остаётся за backend.
- При `409 BOOKING_CONFLICT` введённые данные сохраняются, расписание обновляется, а пользователь
  может вернуться к форме и выбрать другой интервал.
- WebSocket не хранит отдельную копию серверных данных. События создания, отмены и изменения
  доступности инвалидируют кеш комнат, расписаний и бронирований.
- Первоначальное WebSocket-подключение считается штатной загрузкой и не показывает уведомление.
  Баннер появляется только после потери установленного соединения. После reconnect
  выполняется полная REST-синхронизация.
- Отмена бронирования выполняется оптимистично. Перед изменением сохраняется предыдущий кеш, при
  ошибке он восстанавливается, а после завершения данные сверяются с backend.
- `.ics` создаётся на клиенте как UTC-событие iCalendar и скачивается пользователем. Это не
  интеграция с корпоративным календарём.
- Backend не предоставляет атомарный endpoint повторяющихся встреч, поэтому серия создаётся
  последовательными обычными запросами. При ошибке frontend пытается компенсирующе отменить уже
  созданные элементы и затем синхронизирует кеш с backend.
- В development используется same-origin proxy Vite. Для production маршруты `/api/v1` и
  `/api/v1/ws` должны направляться reverse proxy на предоставленный backend; для WebSocket должен
  поддерживаться upgrade, а для API — метод `DELETE`.

## Тестирование

Тесты проверяют пользовательское поведение и бизнес-правила:

- фильтры и преобразование локального времени офиса в API-интервал;
- шаг 15 минут, рабочие часы и горизонт бронирования;
- loading/error/empty-состояния;
- создание, конфликт и отмену бронирования;
- оптимистическое обновление и rollback;
- WebSocket reconnect, resync и обработку событий;
- повторяющиеся встречи и компенсационную отмену;
- формирование iCalendar.

Порог покрытия закреплён в конфигурации Vitest: 80% statements/functions/lines и 75% branches.
